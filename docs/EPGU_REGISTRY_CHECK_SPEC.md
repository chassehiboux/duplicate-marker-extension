# Спецификация: проверка формирования реестров ЕПГУ

## Пользовательский результат

В окне «Сводка ЕПГУ» слева от кнопки «Отправить запросы по неуспешным» появляется
кнопка «Проверить формирование реестров».

Проверка относится только к активной базе («Курган», «Основная» или «ЮРИЦ»), выбранной
в сводке дате и ко всем взыскателям, которые уже показаны в текущей сводке независимо от
статуса запроса ЕПГУ.
Расширение последовательно проверяет только постоянно отображаемые департаменты активной
базы. Департаменты, доступные лишь после включения флажка «Показать скрытые департаменты»,
в проверку не входят.

## Сценарий проверки

1. Перед запуском расширение запоминает исходный департамент и ссылку возврата.
2. Исходное окно ЕПГУ блокируется и показывает прогресс по департаментам.
3. В той же сессии Chrome открывается неактивная служебная вкладка.
4. Служебная вкладка последовательно переключается по всем нескрытым департаментам
   активной базы.
5. Для каждого департамента загружаются все страницы реестров за выбранный день.
6. Для каждого реестра читаются все страницы строк. «Неизвестно» означает жёлтый статус
   «Требуется перепроведение (неизвестно)», «Поиск дела произведен» — красный
   «Требуется перепроведение (поиск дела произведен)». Красный имеет приоритет.
   Это статус в сводке расширения, данные Пирамиды проверка не изменяет.
7. Одинаковые реестры объединяются по системному ID; все найденные департаменты
   сохраняются в одной записи.
8. В обязательном завершающем шаге служебная вкладка возвращает исходный департамент.
9. После успешного возврата служебная вкладка закрывается, исходная вкладка активируется
   без перезагрузки страницы.
10. Открытое окно ЕПГУ сразу перерисовывается и показывает сохранённый результат.

Если один из департаментов не удалось проверить, неполные данные не заменяют последний
успешный результат. Пользователь получает ошибку, а возврат исходного департамента всё
равно выполняется.

Каждый запуск заново проверяет все нескрытые департаменты, включая ранее положительные:
в них могут появиться новые реестры или измениться строки. Ошибка чтения любой страницы
реестра прерывает проверку и не заменяет предыдущий успешный кэш.

## Итоговые статусы взыскателя

- реестров нет — красный статус «Реестры не созданы»;
- все реестры имеют статус «Проведен» или «Проведен (нет данных)» — зелёный статус
  «Реестры проведены»;
- есть «Не проведен», а других ошибочных статусов нет — жёлтый статус «Идет проведение»;
- одновременно есть «Не проведен» и другие неположительные статусы — жёлтый статус
  «Идет проведение, есть ошибки»;
- «Не проведен» отсутствует, но есть пустой или другой неположительный статус — красный
  статус «Ошибки при проведении».

Для совместимости также принимаются варианты «Проведено», «Проведено (нет данных)» и
«Не проведено».

## Раскрывающийся список

Каждая строка взыскателя становится раскрываемой. Справа от статуса запроса ЕПГУ
показываются статус реестров и количество уникальных реестров.

После раскрытия отображается таблица:

| Статус | Департамент | Тип реестра | Имя файла | Действие |
| --- | --- | --- | --- | --- |

Если один ID встретился в нескольких департаментах, реестр показывается одной строкой,
а названия департаментов перечисляются через запятую. Столбец «Департамент» имеет ширину
165 px, длинное значение сокращается многоточием, а при наведении полный список
показывается во всплывающей подсказке — каждый департамент с новой строки.

Статусы отдельных реестров окрашиваются по тем же правилам: положительные — зелёным,
«Не проведен» — жёлтым, остальные и пустой статус — красным. Ширина итогового статуса
взыскателя фиксирована и не зависит от текста или количества реестров. Имя файла можно
скопировать в буфер обмена нажатием правой кнопки мыши по ячейке.

## Проведение отдельного реестра

В каждой строке реестра есть компактная кнопка с иконкой проведения. После нажатия:

1. Расширение запоминает исходный департамент и открывает отдельную служебную вкладку.
2. Вкладка выбирает первый нескрытый департамент, в котором реестр был найден, и открывает
   страницу «Реестры из ФССП».
3. Имя файла вводится в одноимённый фильтр. Из результатов выбирается строка с тем же ID,
   типом реестра и ожидаемым статусом.
4. Нажимаются штатные кнопки «Проведение реестра» и «Провести реестр».
5. Успех подтверждается только после сообщения вида
   «Реестр 19711 - Реестр проведён».
6. Диалог закрывается, таблица обновляется, статус найденной строки читается повторно.
7. Перед закрытием служебная вкладка обязательно возвращает исходный департамент.
8. Новый статус сохраняется в дневном локальном кэше и сразу обновляется в открытом окне
   ЕПГУ вместе со сводным статусом взыскателя.

Если строка не найдена, её тип или статус не совпали, штатное проведение завершилось
ошибкой либо исходный департамент не удалось восстановить, сохранённый статус не меняется,
а пользователь видит понятное сообщение. При неподтверждённом возврате служебная вкладка
остаётся открытой для ручного восстановления.

## Сопоставление взыскателей

Название взыскателя определяется по `ClaimantName`; для файлов формата
`Реестр_ЕПГУ_<взыскатель>_<число>_<число>.xml` используется также взыскатель из имени
файла. Применяются те же нормализация и алиасы, что в эталонном скрипте
`15_check_egpu_departments.py`.

## Локальное хранение

Успешный результат хранится в `chrome.storage.local` отдельно по hostname базы и каждой
доступной дате недельного диапазона.
Он нужен для немедленного обновления открытого окна и восстановления результата после
повторного открытия любой доступной даты недельного диапазона.

Кэш не синхронизируется с Supabase. При открытии функции удаляются только записи старше
доступного недельного диапазона. Повторная успешная проверка заменяет кэш текущей базы за
выбранный день. Успешное проведение отдельного реестра точечно обновляет ту же запись.

## Безопасность и совместимость

- Пользователь во время проверки не работает с Пирамидой; исходная вкладка считается
  временно замороженной.
- Исходный департамент восстанавливается перед закрытием служебной вкладки даже при ошибке.
- Новые permissions не требуются: используются существующие `tabs`, `scripting` и `storage`.
- Основная и Firefox-сборка должны получить одинаковую логику; в Chrome используется
  обычная вкладка той же сессии.
- Новые элементы находятся внутри существующего окна ЕПГУ и скрываются вместе с ним при
  создании скриншота и через пункт F2 «Сводка и повторы ЕПГУ».
