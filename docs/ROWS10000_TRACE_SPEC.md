# Rows10000 Trace Spec

## Цель

Сделать в StageTimer режим "черного ящика" для страниц `https://pyramid.vostok-electra.ru/ovzid/status/*`, чтобы при возникновении подозрительного запроса с `rows=10000` автоматически сохранялся подробный trace последних действий пользователя и внутренних действий jqGrid.

Результат для пользователя:

- пользователь работает как обычно;
- расширение локально держит trace последнего часа;
- пока инцидента нет, наружу ничего не отправляется;
- если пойман инцидент `rows=10000`, trace замораживается;
- в Google Sheets пишется краткая карточка инцидента;
- полный trace сохраняется отдельным JSON-файлом в Google Drive;
- в Telegram уходит отдельное alert-сообщение с `traceId` и ссылкой на trace.

## Почему этого должно хватить

Чтобы понять корень бага, недостаточно логировать только клики пользователя или только сетевые запросы.

Нужно одновременно видеть:

- что нажимал пользователь;
- в каком состоянии был грид перед критичным действием;
- кто и когда вызвал `resetSelection`, `setGridParam`, `reloadGrid`;
- какой именно запрос ушел в сеть;
- что в этот момент было в `selarrrow`, `rowNum`, `postData.filters` и в видимом UI.

Ключевое требование к trace:

- он должен позволять отличить пользовательскую ошибку, сетевую проблему и скрытый клиентский сброс состояния jqGrid;
- для вызовов `resetSelection` и `reloadGrid` должен сохраняться stack trace, чтобы можно было увидеть кодовую точку источника.

## Scope

Логика работает только на страницах:

- `pyramid.vostok-electra.ru/ovzid/status/*`

Наружу отправляется только trace по инциденту. Постоянной потоковой выгрузки событий нет.

## Буфер trace

Локально в памяти вкладки хранится кольцевой буфер:

- временное окно: последние `60 минут`;
- дополнительный hard cap по количеству событий, чтобы буфер не разрастался бесконечно;
- при превышении лимита удаляются самые старые записи.

В trace попадают только полезные события.

Не пишем:

- `mousemove`;
- каждый `keydown`, если он не относится к подтверждению фильтра;
- шумовые DOM-события без связи с гридом.

## Что логируем

### 1. Пользовательские действия

- выбор количества строк (`30/50/100/300/...`);
- клик по чекбоксам строк;
- клик по `Показать выбранные строки`;
- клик по `Сбросить`;
- сортировка колонок;
- пагинация;
- toolbar-кнопки над гридом;
- Enter/подтверждение фильтра по полям таблицы.

Для каждого события сохраняются:

- время;
- тип;
- краткий target;
- текст/значение, если применимо;
- row id / column id, если удалось извлечь;
- URL страницы.

### 2. Внутренние действия jqGrid

Через main-world instrumentation логируются:

- `jqGrid('resetSelection')`;
- `jqGrid('setGridParam', ...)`;
- `trigger('reloadGrid', ...)`;
- `jqGridSelectRow`;
- `jqGridSelectAll`;
- `jqGridLoadComplete`;
- клик по `.showSelectedRow`.

Для критичных операций дополнительно сохраняются:

- snapshot состояния грида до и после;
- stack trace вызова;
- аргументы метода в нормализованном виде.

### 3. Сетевые запросы

Логируются только релевантные XHR/fetch на `ovzid/status/*/data`.

Сохраняются:

- метод;
- URL;
- `_search`, `rows`, `page`, `sidx`, `sord`;
- raw `filters`;
- распарсенные правила `filters`, если JSON валиден;
- статус ответа;
- длительность;
- requestId.

### 4. Snapshot состояния грида

Snapshot должен включать:

- `buttonCounter` у блока `Показать выбранные строки`;
- `selectedRowsVisible`;
- `visibleCheckedCount`;
- `selarrrowLen`;
- первые несколько id из `selarrrow`;
- `rowNum`;
- `page`;
- `sortname`;
- `sortorder`;
- `records`;
- `reccount`;
- `postData.rows`;
- `postData.filters`;
- `activeElement`.

## Правило инцидента

Инцидент `ROWS10000` фиксируется, если выполнено:

- запрос идет на `/ovzid/status/*/data`;
- `_search=true`;
- `rows=10000`;

и дополнительно выполняется хотя бы одно из условий:

- в `filters` есть правило `field=V_OVZID.EDocID`, `op=in`, `data=""`;
- в коротком окне перед запросом был клик по `Показать выбранные строки`;
- snapshot перед отправкой показывает противоречие:
  - `buttonCounter > 0`;
  - `selarrrowLen == 0`.

## Доставка данных

На один инцидент выполняется одна логическая отправка.

Payload содержит:

- summary-информацию для Sheets;
- полный trace;
- служебные поля (`traceId`, версия расширения, пользователь, департамент, URL).

На стороне Apps Script:

1. Создается/обновляется строка summary в отдельном листе инцидентов.
2. Полный trace сохраняется отдельным `.json` файлом в Google Drive.
3. В строку summary записывается ссылка на файл trace.
4. В Telegram отправляется отдельное сообщение с краткой сводкой и `traceId`.

## Формат хранения

### Google Sheets

Отдельный лист, например:

- `Rows10000_Incidents`

Колонки:

- `timestamp`
- `trace_id`
- `base`
- `department`
- `user`
- `page_url`
- `request_url`
- `rows`
- `button_counter`
- `selarrrow_len`
- `visible_checked_count`
- `summary_text`
- `drive_trace_url`
- `version`

### Google Drive

Файл trace:

- формат: JSON;
- один файл на один инцидент;
- имя содержит дату, пользователя и `traceId`.

## Telegram

Отправляется отдельное новое сообщение, не редактируемая сводка.

Сообщение должно содержать:

- тип инцидента `ROWS10000`;
- дату/время;
- пользователя;
- департамент;
- краткую причину;
- `traceId`;
- ссылку на trace в Drive.

## Ограничения

- Решение нацелено на разбор клиентских причин и скрытых jqGrid-рассинхронов.
- Если причина окажется полностью серверной и не оставляет следа в состоянии клиента, trace поможет увидеть только входные условия и факт отправки проблемного запроса.
- Для наблюдаемого сейчас класса проблем этого объема телеметрии должно хватить для воспроизведения и локализации причины.
